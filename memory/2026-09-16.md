# 2026-09-16 — FIX: video nunca reproducía (excepción de inherited widget en initState)

## Síntoma
MP4 de 22 MB: descarga ≈5,6 s y descifrado ≈9,5 s correctos ([VIEWER-PERF]),
pero al entrar al reproductor la pantalla queda cargando indefinidamente y el
video nunca arranca.

## Causa raíz
`_SecureVideoPlayerScreenState.initState()` llamaba `_initPlayer()`, que en su
primera línea (antes del try) hacía `AppLocalizations.of(context)`.
`Localizations.of()` usa `dependOnInheritedWidgetOfExactType` y NO puede
llamarse durante `initState` → excepción no capturada que abortaba
`_initPlayer` antes de crear el `VideoPlayerController` → spinner infinito.

```
Unhandled Exception: dependOnInheritedWidgetOfExactType<_LocalizationsScope>() ...
#5 _SecureVideoPlayerScreenState._initPlayer (lib/widgets/video_player_screen.dart:46)
#6 _SecureVideoPlayerScreenState.initState (lib/widgets/video_player_screen.dart:42)
```

## Corrección
`lib/widgets/video_player_screen.dart`:
- `initState()` vacío (solo comentario). Nuevo `didChangeDependencies()` con
  guard `_didInit` que llama `_initPlayer()` una sola vez. `AppLocalizations.of`
  ya es seguro ahí.
- `_initPlayer()` con todo el cuerpo en try/catch → estado de error
  localizado + `_errorDetail` (texto técnico). Ya no hay fuga de excepciones.
- Tras `initialize()`: log `[PLAYER-PERF] init: Xms`; si
  `controller.value.hasError` se lanza para caer en el estado de error; log de
  `controller.value.errorDescription`.
- Listener `_onControllerChanged` en el controller para errores asíncronos de
  reproducción (pasa a estado de error, nunca spinner).
- `_retry()`: dispose del controller viejo + borra copia propia + reinit.
- UI de error con icono, mensaje localizado, detalle técnico, botón
  `l10n.retry` (Reintentar) y `l10n.backToHome` (Volver al inicio).
- `dispose()` remueve el listener antes de dispose.

l10n (5 idiomas): nuevo `videoPlayerOpenError` en en/es/pt/fr/de. Regenerado
con `flutter gen-l10n`. Se reutiliza `retry` (ya existía).

## Revisión preventiva de otros initState
Auditados los 9 `initState()` del proyecto: `viewer_screen`,
`biometric_settings_screen`, `biometric_lock_screen`, `splash_screen`,
`auth_screen`, `links_screen`, `analytics_dashboard_screen`,
`active_link_analytics_sheet`, `main`. Todos los accesos a
`AppLocalizations/Theme/MediaQuery.of(context)` ocurren en
`addPostFrameCallback`, tras un `await`, o en `build`; no se encontró otro
caso dentro de initState. Único fix necesario: el reproductor.

## Test
`test/widgets/video_player_screen_test.dart` (nuevo, 3 casos):
1. monta `SecureVideoPlayerScreen` y verifica `tester.takeException() == null`
   (regresión del crash de initState);
2. archivo inexistente → muestra `Could not open the video.` + `Retry`, sin
   spinner;
3. tap en `Retry` no rompe y reintenta.
Nota: la carga usa I/O real, hay que ceder el event loop con
`tester.runAsync(() => Future.delayed(...))` antes de comprobar el estado.

## Verificación
- `flutter analyze` → No issues.
- `flutter test` → **75/75 passed**.
- Log en test: `[PLAYER-PERF] init failed after Xms: Exception: decrypted video
  file is missing` (en dispositivo, con archivo válido, será
  `[PLAYER-PERF] init: Xms`).
- Pendiente en dispositivo físico (no disponible aquí): abrir MP4 de 22 MB →
  primer frame y reproducción <5 s tras descifrado, sin la excepción en
  logcat; y probar archivo corrupto → mensaje con Reintentar (no spinner).
- Sin commitear.

# 2026-09-16 (2) — FIX OOM: selección y cifrado de archivos grandes

## Síntoma
`java.lang.OutOfMemoryError` al seleccionar archivos >~50 MB en la pantalla de
subida (`ByteArrayOutputStream.grow` → `StandardMessageCodec.writeValue` →
`GeneratedFileSelectorApiPigeonCodec.writeValue`).

## Causa raíz
`file_selector_android` (`FileSelectorApiImpl.toFileResponse`, línea ~352)
SIEMPRE hace `byte[] bytes = new byte[size]` y lee el archivo completo en el
canal de plataforma. Además el pipeline antiguo multiplicaba copias:
`readAsBytes` → `Uint8List` → `encryptFileInIsolate` (boxing `List<int>`) →
`Uint8List.fromList([...salt, ...nonce, ...ciphertext, ...authTag])`. Para 90 MB
eso son >300 MB transitorios. No hay forma de evitarlo con la API de
`file_selector`, así que se cambió de plugin.

## Solución
- **Dependencia:** `file_selector: ^1.0.3` → `file_picker: ^11.0.2` (resuelto
  **11.0.3**). `file_picker` con `withData: false` copia el content URI a caché y
  devuelve una RUTA real, sin cargar bytes. Soporta AGP 9
  (`isAgp9OrAbove` en su `android/build.gradle`: no aplica el plugin Kotlin).
  OJO API 11.x: es `FilePicker.pickFiles(...)` **estático**, no
  `FilePicker.platform.pickFiles(...)`.
- **`lib/services/secure_encrypt_service.dart`** (nuevo): cifrado AES-256-GCM en
  streaming disco→disco dentro de `Isolate.run`. Formato intacto
  `salt(16)||nonce(12)||ciphertext(N)||authTag(16)`. Chunks de 1 MB (múltiplos
  de 16) + cola; `doFinal` emite bloque final + tag. Calcula el SHA-256 del
  payload en el mismo paso (`sha256.startChunkedConversion` + `_DigestSink`) para
  firmar SigV4 sin releer. Memoria plana (unos MB).
- **`lib/services/file_selection_service.dart`** (nuevo): gateway inyectable
  `FilePickerGateway` + `FileSelectionService` que hace copia por stream a
  `tempDir/ks_picked/` y loguea `[PICKER] copied N bytes in Xms`. Temp dir
  inyectable para tests.
- **`lib/providers/file_selection_provider.dart`** (nuevo):
  `fileSelectionServiceProvider`.
- **`lib/providers/file_provider.dart`**: `_putEncryptedObject` ahora firma con
  el hash recibido y sube `File(path).openRead()` con `Content-Length`
  (`Headers.contentLengthHeader`) → Dio lo respeta para `Stream<List<int>>`
  (dio_mixin `_transformData`). `uploadAndCreateLink` cambia de
  `Uint8List fileBytes` a `String filePath` + `int fileSizeBytes`; cifra en
  streaming, sube, inserta metadata y borra el `.enc` en `finally`. Imports
  `dart:isolate`/`crypto`/`crypto_service` eliminados; `supabase_flutter`
  `hide Headers` (colisión con dio).
- **`lib/features/upload/presentation/screens/upload_screen.dart`**: `_selectedFile`
  pasa de `XFile` a `PickedFile` (path+name+size, NUNCA bytes). El tamaño se
  toma de la metadata del picker (`file.sizeBytes`), no de `readAsBytes`. La
  cámara (`image_picker`) también se stagea por stream (`stageFromPath`).
  `_setSelectedFile` borra el temporal anterior; `dispose` y tras subir OK se
  borra el temporal. `image_picker` importado con `hide PickedFile` (colisión de
  nombre con image_picker_platform_interface).

## Tests
- `test/services/secure_encrypt_service_test.dart` (nuevo, 6): layout
  salt/nonce/ciphertext/tag, hash==sha256 del archivo, round-trip por
  `SecureDecryptService` (fast + streaming), compat byte-for-byte con
  `CryptoService.decryptFileBytes`, password incorrecta.
- `test/services/file_selection_service_test.dart` (nuevo, 4): copia por stream
  de 20 MB con log `[PICKER] copied`, cancelación, `stageFromPath`, `delete`.

## Verificación
- `flutter analyze` → No issues.
- `flutter test` → **85/85 passed** (antes 75/75).
- Pendiente en dispositivo: seleccionar archivo de 50–100 MB sin OOM; revisar
  logcat `[PICKER] copied` y que el build Android con AGP 9 compile con
  file_picker.
- Sin commitear.

## Nota / trade-off
`file_picker` ya copia a caché; hacemos una segunda copia por stream a
`ks_picked/` para poseer el ciclo de vida y poder loguear. Son ~N MB extra de
I/O, pero memoria plana. Si molesta, se puede usar `handle.path` directamente.

# 2026-09-16 (3) — FIX build Android: `cannot find symbol FilePickerPlugin` (file_picker 11 + AGP 9)

## Síntoma
Tras la migración a `file_picker ^11.0.2` (resuelto 11.0.3), `flutter analyze` y
`flutter test` pasaban, pero `flutter run`/`build` fallaba en
`:app:compileDebugJavaWithJavac`:
```
error: cannot find symbol
  flutterEngine.getPlugins().add(new com.mr.flutter.plugin.filepicker.FilePickerPlugin());
symbol:   class FilePickerPlugin
```
(`GeneratedPluginRegistrant.java` es autogenerado, no se toca.)

## Causa raíz (compatibilidad, no un bug "suelto")
`file_picker 11.x` trae en `android/build.gradle`:
```groovy
def isAgp9OrAbove = com.android.Version.ANDROID_GRADLE_PLUGIN_VERSION.tokenize('.')[0].toInteger() >= 9
apply plugin: 'com.android.library'
if (!isAgp9OrAbove) {
    apply plugin: 'org.jetbrains.kotlin.android'   // KGP
}
```
Es decir: asume que con **AGP >= 9** existe **Built-in Kotlin** y por eso NO
aplica KGP. Pero:
- Built-in Kotlin es default en AGP 9, aunque Flutter solo lo habilita
  (`android.builtInKotlin=true`) desde **3.47+**. Este proyecto usa **Flutter
  3.44.2**, cuyo migrator fija `android.builtInKotlin=false` en
  `android/gradle.properties` para seguir soportando KGP legacy.
- Además, la detección de KGP del plugin Flutter
  (`detectApplyingKotlinGradlePlugin`, `FlutterPluginUtils.kt`) busca el texto
  `apply plugin: 'org.jetbrains.kotlin.android'`; como file_picker 11 lo tiene
  (aunque sea dentro del `if`), Flutter cree que el plugin ya aplica KGP y **no
  lo aplica por su cuenta**. Resultado: los `.kt` de file_picker nunca se
  compilan → falta `FilePickerPlugin`.
- 11.0.3 es el último 11.x (no hay fix). Además 10.3.11 está **retirado**
  (retracted) en pub.dev.

Sources: docs.flutter.dev/release/breaking-changes/migrate-to-built-in-kotlin
(Flutter 3.44 añade soporte temporal de KGP con `android.builtInKotlin=false`;
built-in Kotlin real requiere 3.47).

## Solución elegida (Vía B: downgrade a 10.x)
- **`pubspec.yaml`:** `file_picker: ^11.0.2` → `^10.3.10` (10.3.10 = último 10.x
  NO retirado; 10.3.11 retracted). 10.3.10 aplica KGP incondicionalmente
  (`apply plugin: 'org.jetbrains.kotlin.android'`) y soporta Gradle 9 (desde
  10.3.9), por lo que compila con AGP 9 + `android.builtInKotlin=false`.
  Mantiene `withData: false` → devuelve **path**, así que el fix de OOM sigue
  intacto (no `readAsBytes()`; cifrado streaming).
- **API Dart:** 11.x cambió a métodos **estáticos**; 10.x usa la instancia.
  `lib/services/file_selection_service.dart`:
  `FilePicker.pickFiles(...)` → `FilePicker.platform.pickFiles(...)`.
- **Vía A descartada:** alinear a Built-in Kotlin exigiría subir Flutter a 3.47+
  y migrar TODOS los plugins; `purchases_flutter` y `share_plus` aún aplican KGP
  (siguen sin migrar), así que no es viable sin más cambios.

## Fix extra descubierto (release-only, preexistente)
`android/app/build.gradle.kts` referenciaba `"proguard-rules.pro"`, que **nunca
existió** → `:app:minifyReleaseWithR8`: `Supplied proguard configuration does not
exist`. Se eliminó el `proguardFiles(...)` manual: el plugin Gradle de Flutter ya
inyecta `proguard-android-optimize.txt` + `flutter_proguard_rules.pro`
(`FlutterPlugin.kt`) y añade `app/proguard-rules.pro` solo si el archivo existe.

## `dart_test.yaml` (nuevo)
`timeout: 120s`. Los tests de cifrado hacen PBKDF2 (100k) + AES-GCM sobre 3 MB y
en máquina cargada superaban el default de 30 s (2–3 timeouts flaky, sin fallo
de lógica). Con esto `flutter test` queda verde determinista y sin tocar tests.

## Versiones finales
- Flutter 3.44.2 / Dart 3.12.2
- Gradle wrapper 9.1.0, AGP 9.0.1, Kotlin 2.3.20
- compileSdk 36, minSdk max(flutter,23), targetSdk flutter
- `file_picker 10.3.10`

## Verificación
- `flutter analyze` → No issues.
- `flutter test` → **85/85 passed**.
- `flutter build apk --debug` → OK.
- `flutter run -d RZCWA0JFDCJ` (SM A546E, Android 16/API36) → built + installed
  (8.4 s) + launched, sin errores en logcat; 0 errores de registro del plugin.
- `flutter build apk --release` → OK (`app-release.apk`, 95.8 MB) con R8.
- **Pendiente (manual, no automatizable aquí):** smoke test del selector nativo
  → elegir video pequeño → confirmar `[PICKER] copied ...`. No hay
  integration_test y no puedo interactuar con la UI nativa.
- Warning KGP persiste para `file_picker` (10.x), `purchases_flutter`,
  `share_plus`: solo documentado, NO se migran en este cambio.
- Sin commitear (aún).

## Lección
No fijarse solo en "analyze/tests verdes": un plugin con lógica condicional por
AGP puede romper el build aunque el Dart sea correcto. Verificar SIEMPRE el
toolchain real (`flutter --version`, gradle-wrapper, settings.gradle.kts) contra
lo que el plugin asume. `file_picker` 11.x no es compatible con Flutter 3.44 +
AGP 9; usar 10.3.10.
