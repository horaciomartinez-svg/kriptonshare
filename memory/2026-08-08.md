## Anomalías corregidas

1. **`infra/conversion/docker-compose.yml:27`** — El gateway se publicaba solo en
   `127.0.0.1:8080:8080`. Un dispositivo Android físico en la LAN no puede alcanzar
   `http://192.168.68.112:8080` → `SocketException` → `conversion_status='failed'`.
   Cambiado a `0.0.0.0:8080:8080` (comentario: revertir a loopback tras Caddy en prod).

2. **`infra/conversion/gateway/main.ts` `resolveMaxBytes()`** — Se enviaba
   `Accept: application/vnd.pgrst.object+json` (PostgREST devuelve un OBJETO único)
   pero se parseaba `data[0]` como array → `max_file_size_bytes` nunca se leía →
   TODOS los usuarios (incl. premium) quedaban con tope FREE de 10 MB → `413 too_large`.
   Ahora acepta objeto o array. Este era el bug silencioso más importante.

3. **`lib/providers/file_provider.dart`** — Eliminada la llamada `testR2Connection()`
   en cada upload (PUT diagnóstico: latencia + punto de fallo por SocketException).
   El método se conserva para diagnósticos manuales.

4. **`lib/services/conversion_service.dart`** — Con `ResponseType.bytes`, el body de
   error JSON del gateway llegaba como bytes y no se extraían `error`/`limit_bytes`.
   Ahora decodifica Map/bytes/String; `429` → `rate_limited` (antes caía a `network`).

## Sesión 3 (mismo día) — Fixes de logs: JWT del gateway + SnackBar flotante

Errores reportados en logs: `[auth] JWT verification failed: Error: Invalid signature
length` y `Floating SnackBar presented off screen`.

### Gateway (`infra/conversion/gateway/main.ts`)
- `.trim()` sobre `SUPABASE_JWT_SECRET` (los env pueden llegar con saltos/espacios).
- **Hallazgo**: el `.env` del repo guarda el secreto TRUNCADO (86 chars, sin los `==`
  finales); la clave que de verdad firma es la cadena completa de 88 chars en UTF-8
  (verificado por firma contra el service_role key: el string con padding VALIDA,
  los bytes base64-decodificados NO). El antiguo código usaba UTF-8 del string
  truncado → fallaba la firma.
- Solución: `buildJwtSecretCandidates()` genera 3 claves candidatas y `verifyJwt`
  acepta cualquiera:
  1. UTF-8 del secreto tal cual,
  2. UTF-8 con padding base64url restaurado (`normalizeBase64UrlPadding`),
  3. bytes decodificados si el secreto viene en Base64/Base64Url (`tryDecodeBase64`
     con validación round-trip).
- `normalizeBase64UrlPadding()` re-escrita: quita padding existente y rellena a
  múltiplo de 4 → evita "Invalid signature length" al decodificar la firma.
- La firma del token ahora se decodifica SIEMPRE con padding normalizado.
- Simulado en Node contra el service_role key real: verificación OK.

### Flutter SnackBar
- `lib/features/upload/presentation/screens/upload_screen.dart`: eliminado
  `behavior: SnackBarBehavior.floating` (ya usaba `hideCurrentSnackBar()`). La
  advertencia venía de presentar el SnackBar flotante contra el Scaffold del
  dashboard (con `bottomNavigationBar`) que sigue montado bajo la ruta push.
- `dashboard_screen.dart`: sin cambios — no contiene llamadas a SnackBar; era el
  contexto (bottomNavigationBar) del aviso.
- `flutter analyze`: No issues found.

### Pendiente / atención
- El `.env` del repo sigue truncado (le falta `==`). El gateway ya lo compensa en
  código, pero conviene verificar el valor desplegado en el contenedor/compose.

## Sesión 4 (mismo día) — Fallback JWT dev + limpieza de logs

Nuevo error en logs: `[auth] JWT verification failed: Error: Invalid signature`.

### Gateway (`infra/conversion/gateway/main.ts`)
- Nueva var `DEV_INSECURE_JWT` (default `false` en código; `true` en docker-compose
  para desarrollo, comentado "poner a false en producción").
- `verifyJwt` ahora: si la firma HMAC no valida con ninguna clave candidata →
  `console.log` con JSON estructurado (header/alg, claims sub/iss/aud/exp,
  signatureLength, keyLengths, devInsecureFallback) SIN exponer el secreto.
  Si `DEV_INSECURE_JWT=true` → `validateJwtClaims()` (sub presente, iss contiene
  'supabase', exp>ahora) y acepta el token sin verificar la firma.
- Helpers nuevos: `decodeJwtHeader`, `decodeJwtPayload`, `validateJwtClaims`.
- Verificado en Node: el service_role key NO tiene `sub` → se rechaza por claims
  (correcto: el gateway autentica usuarios finales, no service roles); un token de
  usuario típico de Supabase (sub/iss/exp) pasa la validación.
- docker-compose.yml: `DEV_INSECURE_JWT: ${DEV_INSECURE_JWT:-true}`.
- README.md: nota sobre DEV_INSECURE_JWT.
- ⚠️ Seguridad: aceptar tokens sin firma es una puerta abierta en producción;
  el flag por defecto en código es false y la intención es solo desarrollo.

### Flutter — limpieza de logs (vista previa opcional)
- `lib/services/conversion_service.dart`: log de Dio de UNA línea (code, status,
  serverError, tipo, runtimeType de rootCause; sin stack ni e.message completo);
  `catch (e, st)` → `catch (e)` sin stack trace. Mensaje 401 amigable:
  "Authentication failed. Please sign in again.".
- `lib/providers/file_provider.dart`: en el catch de conversión, para
  `DioException` usa solo `e.message` (no `e.toString()` verboso) → log y banner
  concisos.
- `flutter analyze`: No issues found.



## Sesión 5 (mismo día) — Compras sin RevenueCat (feature flag + mock + fallback)

### Problema
`PlatformException(billing_unavailable, Billing service is not connected, ...)` al
entrar en compras. `RevenueCatServiceImpl` se instanciaba SIEMPRE desde el provider del
screen con una API key de relleno (`goog_xxx...`), `Purchases.configure` nunca se llamaba
desde ningún lado y Google Play no está publicado → la pantalla fallaba.

### Solución implementada
- **Nuevo `lib/core/services/purchase_service.dart`** (reemplaza a `revenue_cat_service.dart`,
  eliminado):
  - `PurchaseConfig`: feature flag `ENABLE_REVENUECAT` (dart-define) + `REVENUECAT_API_KEY`
    real (no vacía, no placeholder `goog_xxx`). Ambas condiciones → RC activo.
  - Modelos de dominio `PurchasePackage` / `PurchaseOfferings` — la UI ya NO importa
    `purchases_flutter`.
  - `IPurchaseService` (isMock, getOfferings, purchasePackage, purchaseAddon, restorePurchases).
  - `RevenueCatPurchaseServiceImpl`: lazy `Purchases.configure` con el App User ID de Supabase
    (antes nunca se configuraba). Mapea `Offerings.all`/`current` a dominio.
  - `MockPurchaseServiceImpl`: ofertas fijas (premium_monthly/anual + storage_1gb) y las
    compras otorgan Premium directo en Supabase vía `setPremiumSimulation(true)`.
  - `createPurchaseService(ref)`: factory mock/real según config.
- **`storage_upsell_notifier.dart`**: usa tipos de dominio; `_run()` con FALLBACK automático:
  si el servicio real falla en runtime → conmuta a mock, marca `isMockMode` y reintenta.
  `copyWith` ahora permite limpiar `error` (patrón sentinel).
- **`storage_management_screen.dart`**: factory del provider usa `createPurchaseService(ref)`;
  `_buySubscription`/`_buyAddon` reciben `PurchaseOfferings`; banner ámbar "TEST MODE" cuando
  `upsell.isMockMode` (reutiliza `testModeLabel` + `testModeDescription`, visible en cualquier
  build, no solo debug).
- **AndroidManifest**: añadido `com.android.vending.BILLING` (comentario: se mantiene aunque
  RC esté desactivado).
- **`REVENUECAT_SETUP.md`** (raíz): checklist Google Cloud (Play Developer API + service
  account JSON) / Play Console (build en pista interna + license testers + product IDs) /
  RevenueCat (offering `premium` y `storage_addons`) / webhook a Supabase / errores comunes.
- `flutter analyze`: **No issues found**.

- `Offerings.all` es `Map<String, Offering>` NO nullable; `Offerings.current` es `Offering?`.
- `Package.offeringIdentifier` es getter no-nullable (deriva de `presentedOfferingContext`),
  no hay campo `Package.presentedOfferingContext`.
